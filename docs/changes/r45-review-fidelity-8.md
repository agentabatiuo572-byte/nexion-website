## 方法

- Playwright(借 `Nexion-uniapp` 依赖)真浏览器实测,两站同一套探针脚本、同一口径。
- 主量点 1440×900:我方视口 1455(布局宽 1440,实测 `zoom` 计算值 `min(1440px,1920px)/1440px` = 1),参考站视口 1440(实测无缩放矩阵)。另探 1024 / 1200 / 1920 / 2560,DPR 1 与 2。
- 视觉/动效判据**不开** `reducedMotion:'reduce'`;只有静态几何(区块内衬、栅格、行高)用 reduce 取。
- 滚动一律 `mouse.wheel`(Lenis);每次取值前等 `fonts.ready`,并加**收敛等待**(轮询 scrollY 与目标元素 rect 直至连续多帧不变)——本轮的核心发现正是靠这一步抓到的,不等收敛会读到过渡态。
- 亮区块像素判读用「废 canvas」配方(`addInitScript` 令 `#x-bg` 的 `getContext` 返回 null),并**对照验证过该配方不改变 fx 行为**(同一 scrollY 下开/关配方,视差 transform 逐位相同);暗区块直接截图。
- 对比度、透明度一律读**计算样式 + 合成后像素**,不看渲染观感。
- 参考站只提取机制与数值,本报告不含其代码、文案与图片。

覆盖:首屏 · 导航 · 黑区陈述 · 叠卡 · 白带卡区 · 页脚 · 动效手感 · 首载编排 · 锚点与直达 · 三语 10 条路由 · 5 档视口宽。

## 扣分清单

### 1 · P1 · 新增缺陷(错位 + 行为不稳定)—— 三列视差的落位取决于「怎么到达」,直达 / 刷新后冻结在错位上 · **−0.8**

**类型**:新增缺陷(错位),非拍板项、非上一轮 6 条。属评审可自主执行的类别。

**实测(同一 scrollY,两条抵达路径):**

| 抵达方式 | scrollY | 三列 translateY | 三列屏幕顶差 | 静置 6s 后 |
|---|---|---|---|---|
| 滚轮滚到 | 8560 | −2.2 / −3.9 / −5.4 | **3.2px** | 不变 |
| 瞬时跳到 | 8560 | 28.5 / 99.5 / 213.4 | **184.9px** | 不变 |

**用户实际路径:**

| 路径 | 落位 | 三列顶差 | 正确(收敛)值 —— 同一 scrollY 补发 scroll 事件后实测 |
|---|---|---|---|
| 直达 `/#how` | sy 8383,tops 422 / 484 / 589 | **167px**(+10s 不变) | tops 392 / 383 / 374,**18px**,且**方向相反**(冻结态最左列最高,正确态最右列最高) |
| 从 `/learn/` 点导航「HOW IT WORKS」 | 同上(href 就是 `/#how`) | **167px** | 同上 |
| 中途页刷新(滚动恢复) | 刷新前 0px → 刷新后 168 / 121 / 48 | **120px** | 0px(刷新前的滚轮态即是) |
| 直达 `/#nex` | sy 11792,tops 272 / 377 / 541 | **269px** | tops 230 / 235 / 240,**10px** |
| 直达 `/vi/#how` | tops 458 / 517 / 619 | **161px** | 同 en |
| 直达 `/#trust`(path 两列) | tops −747 / −619 | **128px** | — |

**首次滚动会看到的位移**:直达 `/#how` 后拨一格滚轮(scrollY +1),三列分别跳 **−33 / −113 / −250px**。参考站同一测试为 −1 / −1 / −1 / −1px。

**根因**(`src/scripts/fx.ts:869-874`):

```
const r = el.getBoundingClientRect();
const dy = ((vh2 - (r.top + r.height / 2)) * k) / (zx || 1);
el.style.transform = `translate3d(0, ${dy}px, 0)`;
```

`r.top` **已经含有上一帧写进去的 `dy`**,于是 `dy` 被递归定义:`dy(n+1) = (vh2 − c − dy(n))·k`。它每帧只收敛 `1/(1+k)`(k=0.06 时每帧只走 5.7%),需要几十次 `scroll` 事件才到位;而 `apply()` 只挂在 `scroll` / `resize` / `focusin` 上——**瞬时滚动只触发一次**,停下后再没有事件,就永远冻在半路。滚轮路径能收敛,只因 Lenis 会把一次滚轮铺成几十帧的 scroll 事件。

**这不是「设计不同」,是实现坏了**:强制补发 120 次 scroll 事件让它收敛后,实测位移因子 **0.9435 / 0.9010 / 0.8622**,与理论 `1/(1+k)`(k = .06 / .11 / .16 → 0.9434 / 0.9009 / 0.8621)以及参考站实测 **0.9436 / 0.9013 / 0.8626** 逐位吻合。**k 值与编舞是完全正确的移植,只有收敛路径是坏的。**

**修法(参数级,一行)**:让 `dy` 成为 scrollY 的纯函数——记账当前已写入的位移并从 rect 里减掉:

```
const cur = plxState.get(el) ?? 0;
const dy = ((vh2 - (r.top - cur + r.height / 2)) * k) / (zx || 1);
plxState.set(el, dy);
```

(等价写法:量之前先 `el.style.transform = ''` 再读 rect,但会多一次强制回流。)改完一次 `apply()` 即到位,顺带消掉快滚时约 0.27s 的位移滞后。

**建议**:同族排查——`initPile`(叠卡)以及其它「读 `getBoundingClientRect()` 又往同一元素写 `transform`」的地方是否有同一形态。本轮未逐个查证,只作提示。

### 2 · P2 · 新增缺陷(遮挡 / 不可读)—— 横屏菜单的底缘渐隐永久吃掉主 CTA 的下三分之一 · **−0.3**

**类型**:新增缺陷,**本轮改动引入**(`SiteNav.astro:358-383`「横屏可滚 + 底缘淡出 + 矮屏压缩」)。

**实测(菜单已滚到底,`scrollTop = scrollHeight − clientHeight`):**

| 视口 | 菜单内容高 / 可视高 | 渐隐带起点 | 下载键盒 | 落在渐隐带内 | 键下缘 alpha |
|---|---|---|---|---|---|
| 844×390 | 458 / 390 | y=358 | 326–374(48 高) | **16px** | **0.50** |
| 740×360 | 458 / 360 | y=328 | 296–344 | **16px** | **0.50** |
| 667×375 | 458 / 375 | y=343 | 311–359 | **16px** | **0.50** |
| 390×844 竖屏 | 844 / 844 | y=812 | 466–514 | 0 | 不受影响 |

遮罩 `linear-gradient(to bottom, #000 calc(100% - 32px), transparent)` 绑在**盒**上而非滚动位置,所以滚到底也退不掉:主转化键(菜单里唯一的实心键)下缘恒定半透明,页面正文从键身里透出来(实景截图可见首屏副题压在键上)。

顺带:同一处 `@media (max-height:520px)` 的注释写「压一压,让五项 + 语言 + 下载键**正好装得下,不必依赖滚动**」,实测压缩后内容仍是 **458px**,在 390 / 375 / 360 三档常见横屏高度下分别溢出 **68 / 83 / 98px**,该意图未达成。

**修法(二选一,参数级)**:

- 滚到底撤遮罩:`scroll` 里判 `scrollTop >= scrollHeight - clientHeight - 1` 时挂类去掉 `mask-image`(「下面还有」的提示语义只在没到底时才需要);

### 3 · P3 · 新增缺陷(错位)—— 「当前语言」的柠檬下划线离字 14.7px,压在导航条最下缘 · **−0.2**

**类型**:新增缺陷(错位)。规则本身早于本轮,但**本轮把它推到了主承载位**。

`.lang a.active` 的 `border-bottom` 挂在 `min-height:44uc` 的 inline-flex 盒上:

| 量 | 值 |
|---|---|
| 链接盒 | y 30 → 74 |
| 字行盒 | y 42.3 → 59.3(12px 字) |
| 线的位置 | **y = 74**,即 74px 高导航条的最后一行像素 |
| 字与线的空白 | **14.7px = 1.22em** |

视觉上它不读作「EN 的下划线」,而读作导航条下缘上一条孤立短划。

**与本轮的关系**:dim 档 0.62→0.78 后,EN(1.0)与 VI / 中文(0.78)的透明度差只剩 22%,「当前语言」的辨识几乎全落到这条线上——而这条线的位置是错的。手机菜单里同一条线贴字(该处盒高不同),只有桌面导航有此问题。

**修法**:线画在字上而非盒上——`border-bottom` 换成 `text-decoration: underline; text-underline-offset: 3px; text-decoration-color: var(--x-accent-ink); text-decoration-thickness: 1px`(纸面变体照旧由 `--x-accent-ink` 承担),或给 `.active` 加一层内联 span 承载 border。

**0.78 这个值本身不计分**——它是半透明磨砂下补 AA 的必要修复,属拍板下游。计分的是它的副作用:换档后**悬停中的导航链接(0.6)比静止的语言链(0.78)还暗**,同一行里两组的 hover 反馈一个变暗一个变亮;换档前是 0.6 vs 0.62,两组读起来还是同一族。另外参考站的 0.6 档在我方导航里已经只剩 hover 态存在,静态墨阶从两档变成一档。

**修法**:需主人拍板方向——要么两组统一为「提亮 + 记号」型反馈(链接 hover 保持 1.0、改加下划线),要么接受现状。不建议把语言链压回 0.62(实测暗态 3.98–4.47:1、亮态中灰窗 3.68:1,会退回不过 AA)。
