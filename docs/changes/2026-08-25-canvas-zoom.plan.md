# R42 画布整体缩放(主人 2026-08-25 拍板 A:换机制)

Status: **In progress**

## Why

两轮评审(共 8 份报告)的结论收敛到同一个根因:

> 参考站用**一个整体缩放**做到的事,本站用**三百多条声明逐个模拟**。
> 凡逐条模拟就需要一道能核验每条声明的门;而 CSS 表达长度的方式是无穷的,门永远补不完。

硬证据:机制评审把 R39 那场原始事故**换一种写法原样复活,两道门全绿**——门存在的理由被证伪。
两轮分数 3/4 下降,且每轮修复都在造新伤(R41 我一轮造了 4 条)。

## 关键实测:用 `zoom` 而不是 `transform`

主人批准 A 时,我给的代价清单是按 `transform` 估的(要重写钉屏、挪固定层、改坐标逻辑、加 JS 补高)。
动手前实测发现 **`zoom` 更省**,且方向完全一致:

| 边界 | `transform: scale()` | `zoom` |
|---|---|---|
| 影响布局高度 | ❌ 不影响 → 必须 JS 补高 | ✅ **影响** → 零补高 |
| `position: sticky` | ❌ **直接失效**(三种外层写法逐个实测) | ✅ **成立** → 叠卡编舞**不用重写** |
| 画布外 fixed 层 | 需挪出 | 本就在外,不受影响 |
| 居中 | 需 margin 计算 | `margin-inline: auto` 即可 |
| 窄屏 | 需另设 | 媒体查询按**真实视口**生效,断点以下 `zoom:1` 自适应 = 今天的行为 |

⚠️ 唯一注意点:**画布内的视口单位会被二次放大**(实测 `100svh` 在 zoom 1.3333 下渲染成 1333)。
全站仅 4 处用到,逐处改写。

## 目标形态

```
body
├─ canvas#x-bg      ← 固定层,全出血,画布外
├─ .site-nav        ← 固定层,全宽;内层套自己的画布(条内文字随画布缩)
└─ .x-canvas        ← width:1440px; margin-inline:auto; zoom: min(100vw,1920px)/1440px
     ├─ main
     └─ footer
@media (max-width: 1199px) { .x-canvas { width:auto; zoom:1 } }   ← 断点以下=今天的自适应布局
```

一切尺寸回退成**1440 画布上的固定像素**。`--u` / `--uc` / `--x-gut` 三个 token 全部删除。

## 分期

- **P1 地基**:Base 加画布壳 + zoom + 断点;导航内层套画布;验证居中/吸顶/手机端
- **P2 拆脚手架**:329 处 `calc(N * var(--u|--uc))` 回退成 `Npx`;删三个 token;删 main 的留白内边距

## Done-when

1. 1440 处渲染**逐像素等于 R39 基线**(scale=1,理论恒等,须实测)
2. 1920/2560/3440 下所有尺寸 = 1440 值 × min(vw,1920)/1440,**含字号/盒子/边框/渐变止点/栅格**

# 实施结果

Status: **Implemented**(待第三轮评审)

## 与计划的偏差(交底)

主人批准 A 时我给的代价清单是按 `transform` 估的。动手前实测发现 **`zoom` 更省**且方向一致,
于是改用 zoom —— 原计划里「重写钉屏 / 挪固定层 / 改 7 处坐标逻辑 / 加 JS 补高」**一件都没做**,
因为 zoom 影响布局(零补高)且不破坏 sticky(叠卡编舞原样保留)。

## 落地形态

```
body
├─ canvas#x-bg            固定层,全出血(画布外)
├─ .site-nav              固定层,幕布全出血;内层 nav 自套一份画布
└─ .x-frame               全宽裁切框 —— 停放的叠卡裁在**屏缘**
     └─ .x-canvas         width:1440px; margin-inline:auto; zoom: var(--x-zoom)
          ├─ main
          └─ footer
--x-zoom = min(100vw,1920px)/1440px;@media (max-width:1439px) → zoom:1, width:auto
```

断点定在 **1440**:那里画布宽=视口宽、zoom 恰为 1,**两条曲线天然接合,裂缝在构造上不存在**。

## 实测结果

| 项 | 结果 |
|---|---|
| 画布几何 | 2560 → 画布左 320 宽 1920;3440 → 左 760 宽 1920;页高在 1920 以上冻结 |
| 裂缝 | 1439→1440→1441 页高变化 **0.1%**(R41 在 1200 处是 16.7% 硬跳变) |
| 横向溢出 | **33 路由 × 6 档宽度 = 0** |
| 控制台 | 8 档宽度 × 33 路由 **零报错** |
| 最小可见字号 | 11–16px(R41 在 1200–1439 段掉到 10px) |
| 触达 | 全宽度 ≥44 画布像素(R41 曾掉到 36.7) |
| 叠卡 | 吸顶正常、编舞收在 0.85、无死区;单位换算后不再跑快一个缩放倍数 |
| **首屏词梯** | 基线首页 15 个标题中 **13 个是词梯**(标题总高 2858px);修后 **0 个**(1027px)——整页永久虚高约 1000px 的缺陷根治 |
| 内页 1440/390 页高 | 与 R39 基线 **0.0% 相同** |

## 门随机制换代

- **静态门**:从「查每条声明的形态」换成「画布内禁视口单位」——整体缩放下,画布内任何 px 都自动是画布像素,
  「配对值掉队」整族按构造消失,旧判据失去存在理由。新判据小而确定,**6 种危险写法红测全拦、3 种合法写法零误报**。
- **运行时门**:七判据(画布/溢出/等比/冻结/可读/触达/**连续**)。
  🔴 连续判据**从产物 CSS 读出所有断点**逐个探,不写死缝的位置 —— 写死正是 R41 那道缝溜过去的失效模式。
  五条关键判据红测全拦(含「把断点挪回 1200 重现裂缝」)。
- 门在「读不到断点」「sitemap 为空」时**判红而非静默放过**,该设计当轮即救场一次(构建把媒体查询压成了新式区间写法)。

## 本轮我自己踩的坑(留痕)

1. 换算式 `100svh * 1440 / min(...)` 在 CSS 里**是无效值**(长度÷长度得纯数,再减长度非法),整条被丢弃 → 吸顶失效。
   改为抽出 `--x-zoom` 单一真源。
2. 横向裁切放 `body` 无效 —— body 的溢出属性会被**上交给视口**,body 自己反而不裁(实测溢出 5153px)。改用全宽裁切框。
3. 天花板形态转换**目标形式选错**,断点以下丢掉流体行为,手机端页高 +19~28%。用改动前后差异对照逐条改正。
4. 改正又**过度应用**到导航 LOGO 的触达高度上(掉到 32px),被新门当场抓住。
5. 探针没等平滑滚动收敛(本站 1.2 秒缓动),一度误判叠卡坏掉。
