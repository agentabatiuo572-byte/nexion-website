## 方法

| 项 | 做法 |
|---|---|
| 文字对比度 | **显字 / 藏字求差**:同一裁切框拍三次 —— A(显)/ B(`-webkit-text-fill-color: transparent`,只灭字形填充)/ C(再显)。A 与 C 差 >12 的像素直接剔除(流光在两拍之间移过),剩下按 \|A−B\| 排序取**前 10% = 字形芯**,逐像素算「显字色 vs 藏字色」,报 min / p10 / med。不读计算样式(漏 opacity 稀释),不用 `visibility:hidden`(会连护字层一起灭) |
| 行间挤压 | DPR 3 截图 → **横向投影求墨行带**(阈值 <150)→ 带间空隙换算回 CSS px。这样量到的是**字形墨迹**的间距,不是行盒间距(叠音符/下点根本不在行盒里) |
| 判据落在输出侧 | 叠卡不量「我写进 CSS 的 top」,量**用户看到的卡顶 / 品名 / 价格 / 倍率行的 rect**;矮屏不量 media 里写了什么,量**产物的 computed padding + 元素 bottom vs 视口高** |
| 滚动 | Lenis 在管:`mouse.wheel` 逐步逼近 + 收敛等待;`window.scrollTo` / `scrollIntoView` 在桌面**根本不动**(实测,已弃用);视差层里的元素还会随滚动反向漂,用「读 rect → 再修正」的闭环把目标带进视口 |
| 拖滚动条 | 真的按住经典滚动条滑块拖(带反馈定位到白带边界 ±3px),再做 ±1/±2/±4/±8/±20 轨道像素、60–900ms 半周期的往复 |
| 翻色竞态 | 每帧读 `on-light` + 同帧读白带 rect,状态与几何成对取 |
| 视口 | **1366×700**、1440×768、1440×900、1455×1300、1920×900、2560×1440、390×844、**844×390**、**740×360**、768×1024,另加 667×375 / 360×640;桌面全程 `ignoreDefaultArgs:['--hide-scrollbars']` **经典滚动条**;DPR 1 与 2/3 各跑 |
| 未开 | 视觉判据全程**不开** `reducedMotion:'reduce'`(reduced 单独一轮只查降级) |

脚本:`…/scratchpad/rev3k-*.mjs`(lib / contrast-lib / deck / deck2 / deckshot / hero / heroink / beats / beats2 / mobile / mobile2 / herobox / nav / seam / seam2 / ctr / sweep / inter / lb2 / nav2 / misc / lines / lines2 / lines3 / vi-lines / drag / drag2 / drag3 / learn / hover / hover2 / vlink / vlink2 / vlink3 / vlink4 / kbd / cls / shots)。

### #1 `-0.9` · 横屏手机首屏:下载整行仍在折叠线外,**为它写的修法是一条死声明**

**类型:新增缺陷(上一轮修法未生效)** · 非已拍板项(B2 拍板的是「底空 220」这个值,矮屏分支不在其内)

实测(经典滚动条,产物侧 computed):

| 视口 | `.hero` computed padding-bottom | 下载行 bottom | 视口高 | 折叠线外 |
|---|---|---|---|---|
| 844×390 | **39px** | 443.8 | 390 | **54px** |
| 740×360 | **36px** | 423.9 | 360 | **64px** |
| 667×375 | **37.5px** | 410.9 | 375 | **36px** |
| 390×844(竖屏,对照) | 84.4px | 692.1 | 844 | 0 ✅ |

**根因**:`HeroSection.astro` 里

- **第 52–56 行** `@media (max-height: 520px) { .hero { padding-bottom: max(60px, calc(120 * var(--u))) } }` ← 本轮为横屏加的分支
- **第 151–157 行** `@media (max-width: 860px) { .hero { … padding-bottom: 10svh } }` ← 早就存在的基础分支

两条同选择器、同属性、**同特异度**,媒体查询不加特异度 → 同一 `<style>` 里**源序决胜,后写的 10svh 赢**。而横屏手机恰好**同时满足**两个条件(宽 ≤860 且高 ≤520),于是那条新分支在它唯一要服务的场景里**一次都没生效**:844×390 算出来该是 70.3px,产物是 `10svh = 39px`。上一轮量到 445、这一轮量到 443.8 —— 差 1.2px,正是「什么都没改」。

**同一个修法在 `SiteNav.astro` 里是做对的**:那边的 `@media (max-height: 520px)`(第 437 行)已经移到 `.links a`(398)/`.row2`(408)之后,所以菜单那一半确实修好了。**两个文件用同一套修法,只改了其中一个。**

**顺带:光挪位置也不够。** 844×390 的内容块本身是 `padding-top 80 + 内容 364 = 444`,即使把底空清零也超出 390。要真正装下需要再收 54px(740×360 收 64、667×375 收 36)。

**修法(参数级)**:把 `@media (max-height: 520px)` 整块移到 `@media (max-width: 860px)` **之后**,并把上边距与簇内间距一起收:

```css
/* 放在第 151 行那个 @media (max-width: 860px) 块的后面 */
@media (max-width: 860px) and (max-height: 520px) {
  .hero { padding-top: calc(44 * var(--uc)); padding-bottom: max(24px, 6svh); }
  .cluster { gap: calc(12 * var(--uc)); }
}
```

**机器门在这一族上有盲区(建议一起焊)**:`scripts/gate-css-shadowed.mjs` 的判据 B 只在两处的 `@media` 条件**字符串全等**、或一方的条件集是另一方的**超集**(`narrowerThan`:`B.every(c => A.includes(c)) && A.length > B.length`)时才报。`(max-height: 520px)` 与 `(max-width: 860px)` 是**正交条件**,互不为超集 → 第 156 行的 `if (!same && !aNarrower) continue;` 直接跳过。建议补一条 **B3:两处条件正交但交集非空(一条只约束 width、另一条只约束 height,或数值区间相交),先写的那条在交集里必输** —— 本轮这一条正是靠逐视口量 computed 值才抓到的,和门注释里那两次同型。

**严重度**:这是全站唯一的转化动作,横屏访客首屏一个下载入口都看不到;叠加 #2,360/375 高的横屏访客两个入口都要滚。

### #3 `-0.6` · 越南语卡内正文:mono 1.2 把行间墨迹间隙压到 **0.33 CSS px**

### #4 `-0.4` · 首屏四拍在慢网上**次序颠倒**,标题空白窗口被拉长到 1.7–2.1s

**类型:新增缺陷(本轮拍板项 ⑤ 把标题拍 500 → 900 引入)** · 拍板的是「900ms」这个值,不是「在慢网上排到副题后面」

两个拍点挂在**两个不同的钟**上:

- 副题 / 下载行 / 数字条:`html.x-boot` 的 CSS 动画 `x-fade 0.5s ease 1.4s`,锚点 = **元素首次渲染**(≈FCP);
- 大标题:`fx.ts` 的 `setTimeout(play, BOOT_T0 + 900 - now)`,`BOOT_T0 = performance.now()`,锚点 = **fx.ts 模块执行时刻**。

两个锚点相差的就是 JS 的到达延迟。标题拍 500 时能容忍 900ms 的 JS 延迟,**改成 900 后只剩 500ms**。实测(每档一次完整加载,1440×900):

| 带宽 | FCP | 标题 90% 可读 | 副题/下载 90% | 标题领先 | 空白标题窗口 |
|---|---|---|---|---|---|
| 本地 | 112 | 1311 | 1810 | **+499ms** | 1.20s |
| 5 Mbps | 752 | 2268 | 2452 | +184ms | 1.52s |
| 3 Mbps | 776 | 2351 | 2484 | +133ms | 1.58s |
| **1.5 Mbps**(评审指定档) | 896 / 884 | 2627 / 2642 | 2610 / 2593 | **−17 / −49ms** | 1.73 / 1.76s |
| 0.75 Mbps | 1120 | 3192 | 2826 | **−366ms** | 2.07s |
| 0.4 Mbps | 1528 | 6189 | 3240 | **−2949ms** | 4.66s |

vi 0.75 Mbps −632ms、手机 1.5 Mbps −33ms、手机 0.75 Mbps −349ms,同型。也就是说:**在评审自己指定的 1.5 Mbps 档上,四拍已经不成立了** —— 副题和下载键先于大标题落地,而访客盯着的那块最大的字空 1.7 秒。

**修法(参数级)**:把标题拍挂到**和 CSS 拍同一个钟**上,而不是 fx 的执行时刻:

```ts
// fx.ts:BOOT_T0 附近
const PAINT_T0 = performance.getEntriesByName('first-contentful-paint')[0]?.startTime ?? BOOT_T0;
// 播放时:两个锚点取小,慢网下就不会排到副题后面
s.timer = window.setTimeout(play, Math.max(0, Math.min(BOOT_T0, PAINT_T0) + delay - performance.now()));
```

或者更彻底:让标题也走 `html.x-boot` 的 CSS 时间线(与副题同源),JS 只负责建遮罩。**桌面本地档的 +499ms 领先不受影响**(两个锚点在本地几乎重合)。

附:0.4 Mbps 下还有一个连带现象 —— `[data-lr='load']:not(.lr-ready)` 的 3s 兜底会先把纯文本显出来,fx 到达(≈5s)时建遮罩又把它藏回去,6s 才滑入,屏上是「出现 → 消失 → 再滑入」。这一条是既有兜底的固有形态,只在 BOOT_T0 > 3s 时才够得着,不单独计分。

### #5 `-0.2` · 行内链的 44 命中盒吃掉上一行文字的下半截

**类型:既有值(本轮 ③ 把它从 6.4px 加深到 7.3px)** · 非已拍板项

`.vlink` 用「padding 14.8 上下 + margin −6.6 / −23」凑出 44 命中高且占位高不变。注释写的是「上面只借 6.6px(上一行的**降部区**)」,但那 6.6 是相对**行盒**算的,而行高收到 1.2 后行盒(14.4)比字的内联盒(17)**还矮**,半行距变成 −1.3 —— 实际借走的是内联盒底部的 **7.2–7.3px**。`elementFromPoint` 逐行扫(x 取链接盒内 +30):

| 页面/视口 | 上一行内联盒 17px 里被 `.vlink` 接管的行 | 实际重叠 |
|---|---|---|
| `/` 1455×1300 | 第 10–18 行 | 7.2px |
| `/` 1440×900 | 第 10–18 行 | 7.3px |
| `/vi/` 1440×900 | 第 9–18 行 | 7.3px |
| `/` 390×844 | 第 9–17 行 | 7.2px |
| `/zh/` 1440×900 | 第 13–18 行 | 4.7px |

12px Space Mono 的基线在内联盒 ≈13.5 处,命中盒从 9.8 起 —— 也就是**盖到基线以上 3.7px**,约等于小写字身高度(x-height ≈6.2)的 60%,不只是降部区。后果:读者点(或拖选)正文最后一行的下半截会跳到 `#trust`。改前(行高 1.45)重叠 6.4px,本轮 +0.9px。

**修法(参数级)**:命中高与占位高都不变,只把借用从「上一行」挪到「下面的空白」(`.step` 那 40px gap 是空的):

```css
.vlink { margin: calc(-2 * var(--uc)) 0 calc(-27.6 * var(--uc)); }  /* 原 -6.6 / -23 */
```

`14.4 + 14.8×2 = 44` 不变,`44 − 2 − 27.6 = 14.4` 占位高不变,盒顶只探到上一行行盒下缘外 2px(纯空白)。
