## 🔴 P1

### P1-1 · E3「下载探活」在驾驶舱完全缺席(功能未实现,不是显示问题)

- **规格**:CON03-A1 要求运营健康卡含「下载链接探活」;CON03-E3 定义「任一已启用下载 URL 探活连续 2 次失败 → 红条『{平台} 下载链接不可达(最近核验 {时间})』,点击 → /content/downloads」;CON03-③ 定义探活 = **worker cron 每 6h HEAD**;T20 的 AC 原文写着「下载探活红条跳 /content/downloads」。
- **实测**:
  - `admin/src/pages/dashboard.tsx` 全文 0 处出现「探活 / probe」;
  - `/api/dash` 响应体无任何探活字段(9 组 section 全部抓取核对);
  - `worker/wrangler.jsonc` 只有 `"crons": ["10 0 * * *"]`(日汇总),**没有 6h 探活 cron**;
  - 没有任何表或 KV 存「连续失败次数」与「最近核验时间」——「连续 2 次失败」这个状态在系统里根本不存在。
- **现存的只有** CON05 的按需探活(`worker/src/config.ts:142` `/api/config/probe-downloads`),挂在 /content/downloads 页面的「立即探活」按钮上,**需要人主动去点**。
- **根因形态**:`worker/src/dash.ts:169` 的注释写「探活由前端按需触发,这里给规则/统计」,把责任推给前端;前端没接。两边都以为对方做了。
- **影响**:官网唯一转化路径(商店链接)挂掉时,驾驶舱不会有任何提示——这正是这条 AC 存在的理由。

### P1-2 · 「今日实时」的点击数把 bot 算了进去(与次日汇总自相矛盾)

- **实测**:注入 3 条今日 `cta`(2 条 `bot=0`、1 条 `bot=1`)→ 卡显示 `点击 3`,**应为 2**。同一批 `pv` 的 bot 那条被正确排除(`pv 3 / uv 2`,期望值一致)。
- **代码**:`worker/src/dash.ts:192`

  ```sql
  SELECT COUNT(*) n FROM raw_events WHERE type='cta' AND ts >= ?1
  ```

  紧邻的 189 行 pv 查询有 `AND json_extract(payload,'$.bot') = 0`,cta 这条漏了。
- **与两处权威冲突**:
  1. PRD CON03-③:「Bot 占比 | …命中者**不入流量指标**,只入此占比」;
  2. `worker/src/rollup.ts:94-95` 次日汇总对 cta 明确 `if (isBot) break`。
  也就是说:今日预览与它自己声明的权威(「口径以次日汇总为准」)对同一指标算法不同——爬虫刷一波,今天看到点击暴涨,明天自己掉回去。
- **同卡内也不自洽**:同一张「今日实时」卡,UV 排 bot、点击不排。
- **修法**:把 189 行那句 `json_extract(payload,'$.bot') = 0` 补到 192 行。(`blocked` 那条不需要,它本就是独立分桶。)

### P1-3 · Bot 占比是「日均值」冒充「期间请求占比」,且是全页唯一没标口径的比率

- **规格**:CON03-③「Bot 占比 | UA 命中已知爬虫表的**请求占比**」= 期间请求级占比。
- **实现**:`worker/src/dash.ts:171` `SELECT AVG(bot_share) FROM daily_bot …` = 各日占比的**无权重算术平均**。
- **实证**(tester 造数):

  | 日 | daily_bot.bot_share | 当日人类 pv | 反推 bot pv |
  |---|---|---|---|
  | 08-25 | 0.05 | 160 | 8.42 |
  | 08-27 | 0.10 | 120 | 13.33 |
  | 08-30 | 0.90 | 90 | 810 |

  - 页面显示 **35.0%**(=(0.05+0.10+0.90)/3);
  - 按 PRD 口径的请求加权占比 = 831.75 ÷ 1201.75 ≈ **69.2%**。
  - **差近 2 倍**,而且显示成带一位小数的「35.0%」这种精确长相——AC-F 要抓的「看起来精确但实际是估算」在本页只命中这一个。
- **标注面对照**:全页 8 处口径标注全部在场(下载点击 ×2、北极星、UV 按日相加、p75 不跨天平均、今日实时、洪水下为下限、匿名无 cookie),**唯独 Bot 占比既算错又没标**;卡上唯一的说明是「已排除出流量」,说的是另一件事。
- **结构性**:`daily_bot` 表只有 `(date, bot_share)`,**没存分子分母**,所以按当前 schema 算不出正确的期间占比。修法要么给表加 `bot_hits`/`total_hits` 两列(合 PRD 口径),要么卡上老实标「按日占比的平均值」(降级为诚实但不合规格)。前者才是 PRD 要的。

## P2

1. **空库时质量卡/健康卡的「0」与「—」混用** — AC-A 要求质量卡显「—」。实测 LCP/CLS 是「—」✔,但同卡的「JS 报错 **0**」「404 命中 **0**」、以及运营健康的「被屏蔽请求 **0**」显示为 0。零流量下这三个 0 读起来像「站点没报错」的肯定断言,实际是「一条数据都没有」。PRD ④「永不编造/插值缺失数据(缺即『—』)」。
2. **内容榜四卡共用一个 section,一张表挂了四张卡一起黑** — `DROP TABLE daily_page` 后,页面 PV 榜 / 板块曝光 / FAQ 榜 / 学习中心阅读榜一起塌成一张「内容榜 · 本卡数据查询失败」。而 `daily_section`/`daily_faq`/`daily_learn` 三张表**完全健康**——同一次响应里漏斗卡还在用 `daily_section` 正常出 94/31。PRD ⑤「单卡查询失败**只红该卡**」。「整页不被拖垮」这条判据 pass,粒度不达标。
3. **今日实时查询失败时无重试出口** — PRD CON03-E2 原文「今日列显示『—』+ **重试**」。实测把 `raw_events` 改名制造失败后,卡内显示「查询失败」四个字:既不是「—」也没有重试按钮。**核心诚实性没破**(确认没画成 0),但用户没有恢复出口,只能整页刷新。
4. **按日趋势卡在 30/90 档静默截断到最近 10 天** — 卡角标写「11 天有数据」却只画 10 行;窗口内 UV 最高的那天(08-10,UV 999)完全看不见,且所有可见柱子按那个**看不见的 999** 做归一化 → 全被压扁成小条。页面无「仅显示最近 10 天」字样。90 天档尤其形同虚设。
5. **屏蔽在驾驶舱缺「占比」与常驻「详情」入口** — PRD A1 列「屏蔽卡(拦截数/**占比**/TopN)」、⑥ 列「屏蔽卡『详情』→ /geo 定位统计区」。实现把屏蔽并进运营健康,只有拦截数与 TopN,**没有占比**;去 /geo 的链接**只在 degraded 告警条上出现**,规则正常时无入口。(数据源没问题:/geo 页自己有「占近 7 天流量 X%(口径:拦截数 ÷ 拦截+人类访问)」,是驾驶舱侧的缺口。)
6. **「最近发布 v1:成功」在从未发布过的库上就出现** — v1 是 `worker/src/config.ts:28` 首访自动种下的种子行(`created_by='system'`、`reason='初始种子(=上线前站内容)'`),不是一次真发布。全新库首开驾驶舱即显示「最近发布 v1:成功」,把没发生过的事说成发生了。另:`lastPublish` 取的是 `ORDER BY id DESC LIMIT 1` = 最新**版本**而非最新**发布**,后续 T21 引入 `validating`/`failed` 态后,「最近发布」卡会照原样吐状态字面量。建议种子行改按「初始版本」措辞,或只取 `created_by != 'system'` 的行。
7. **「下限」口径标注离它修饰的数字太远** — 「单来源洪水流量下拦截与 404 计数为下限」只在页面最底部的小字总说明里,而「248 被屏蔽请求」「24 404 命中」两个数字在上面的卡里,卡上无任何标记。AC-F ③ 判 **在场 = pass**(已回源确认 `worker/src/index.ts:13,80` 与 `worker/src/geo.ts:61` 两处确实都是 120/分/IP 节流,这句话属实),但读数的人多半看不到。

## 观察项(不计 P,供实现方参考)

- **O1** 单卡「重试」实际是**整页重查**(`load(range)` 会 `setD(null)` 走骨架再拉全量),不是 PRD ⑥ 说的「重查该卡」。因为只有一个聚合端点,粒度化需改 API;功能上恢复正确——实测四张内容卡全回来、其余卡无副作用、`console` 0。
- **O2** 分语言 UV 占比取 0 位小数,47% + 46% + 6% = 99%,四舍五入不合 100。
- **O3** 页面 PV 榜只显示 `path` 不显示 `locale`(API 里 locale 是分组键之一),同 path 不同语言会渲染成两行长得一样的条目。当前站 vi/zh 走 `/vi/` `/zh/` 前缀所以撞不上,但榜是按 `(path, locale)` 分组的,契约上可撞。
- **O4** **趋势不做零填充**——窗口内没有数据的日期直接不出现(30 天档实测 08-10 后直接跳 08-17),没有把「没数据」画成 0。这是对的,值得保留。
- **O5** `p75` 的处理是本次实现里最诚实的一处:取最近一天而非跨天平均,并在卡上把「取最近一天(日期)/ 样本 n / p75 不能跨天平均」三件事全写了出来。P1-3 的修法建议照抄这个范式。

  |---|---|---|
  | 数字 | `blocked > 0 \|\| geo?.enabled ? num(blocked) : '—'` | → `—` |
  | 占比 | `blockedShare !== null`,而 `blockedShare = blocked + pv > 0 ? blocked/(blocked+pv) : null` | → `0.0%` |

- **现实可达性**:屏蔽规则默认未启用,官网正式有流量后**这就是常态画面**,不是边角场景。全空库时因为 `pv=0` 反而两边都不显示,所以只在「站上线了、没开屏蔽」这段时间暴露——恰好是最长的那段。
- **口径性质**:与本轮已修的 P2-1 是同一族(「0 与『—』混用会让『没数据』和『真的是零』分不清」——这句是修复 commit 自己的话),只是搬到了隔壁字段。
- **修法**:占比与数字共用同一判据(数字显「—」时不渲染占比),或两边都改成「geo 未启用 → 该组整体不展示」。
