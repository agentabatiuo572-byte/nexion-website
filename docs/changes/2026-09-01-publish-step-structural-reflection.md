# 结构性反思 —— 发布上报接口(第五轮后强制触发)

- **触发条件**:「两个各自正确的修法合起来造出新故障」**第四次**出现(死锁 → 假红条 → 重发打死执行器 → 终态重发打死执行器)。
  按铁律,同型 ≥2 轮复发必须**先停下反思整个方案是否有方向性偏差或结构性错误**,产出书面结论才允许继续。
- **状态**:结论已出,判定为**结构性问题**,先改结构再继续。

---

## ① 拆到不可再拆的事实:什么结构让这个「不小心」必然发生?

`POST /api/publish/step` 上现在有**六道相互独立的校验**,它们是四轮里一条条累加上去的:

1. 锁存在且属于本版(r2)
2. 锁未过期(r2)
3. 上报者是领过单的那个执行器(r3)
4. 前序步骤全部 ok(r2)
5. 同一步同一结果 → 幂等成功(r4)
6. 其余重复 / 改口 → 拒(r2/r4)

**它们是一串按固定顺序求值的否决条件,不是一张明确的状态转移表。**
于是「合法与否」这件事没有任何一处被完整表达出来——它是六个 `if` **副作用式地**拼出来的,
而每加一条,与已有五条的交叉都要靠人脑现推。四次组合故障,四次都出在交叉处。

第四次的具体形状:**幂等(第 5 条)排在锁归属(第 1 条)之后**,
而每个**终态**回报都会先删锁 —— 所以终态回报的重发**根本走不到幂等**,
必然撞上第 1 条返回 `not-current-job`。
更糟的是「响应会丢」在当前配置下恰好只发生在 `swap ok` 那一拍
(伺服目录改成 `dist-live` 后,唯一会写它的就是切换步,写入触发开发服务器重载)。
结果:**一次完全成功的发布把常驻执行器打死了。**

## ② 为什么前三次的修法没挡住第四次?

前三次都修在**症状层**:哪条路被堵死了就给哪条路开个口子。
- 第一次:加「强制中止」出口;
- 第二次:并发被拒不留垃圾行;
- 第三次:同一步同一结果判幂等。

每一次都对,每一次都只覆盖了**我当时想到的那一条交叉**。
症状层的修法数量 = 我想到的交叉数量;而交叉的真实数量 = 校验条数的组合数。
**只要还是「一串 if」,第五次就一定会有。**

## ③ 同族还有几个没被发现?

把这一族抽象成:**「(已记录状态 × 本次上报状态 × 锁状态)三元组里,有多少格没被想过?」**

- 已记录状态:`无 / running / ok / failed` = 4
- 本次上报:`running / ok / failed` = 3
- 锁状态:`本版持锁 / 无锁(终态已删) / 锁属他版 / 锁已过期` = 4

**48 格。** 现有测试覆盖了其中不到十格,其余全靠「读代码觉得没问题」。
第四次组合故障就落在「已记录=ok × 上报=ok × 无锁」这一格——**一格没被想到,就够打死执行器。**

## ④ 能不能用一条不变量或一道机器门根治?

能,而且这一族就该这么治:

**改结构**:把「这次上报合不合法」从六个 `if` 收成**两层、一张表**:

- **第一层(与锁无关)——幂等与转移合法性**:只看 `publish_steps` 里这一步**已经记成什么**,
  与本次上报比对,得出三种结论之一:`已受理(幂等)` / `可以写入` / `非法转移`。
  🔴 **幂等必须在这一层**,因为「这条回报到底有没有被记下」是一个**关于记录的事实**,
  与锁还在不在、谁持锁**完全无关**。终态删锁不该让「我上次到底成功了没」变得无法回答。
- **第二层(仅当第一层判「可以写入」)——授权与时序**:锁归属、锁未过期、领单口令、前序顺序。
  只有真的要**改变状态**时才需要授权;重发一条已经生效的回报不改变任何状态,不需要授权。

**焊门**:表驱动测试**穷举** 4×3×4 = 48 格,每格声明期望结论。
不是抽样,是穷举——这一族的教训正是「抽样等于只测我想到的那几格」。

## 与「路线是否选错」的结论

**路线没错**。worker 编排状态机、执行器在外面干活、服务端核实结果——
这条路在 Cloudflare Workers 跑不了构建的前提下是唯一可行的,四轮验收也证明了
「HTTP 面上不了线」这条机器强制成立(P0 连续三轮为 0)。
错的不是路线,是**上报接口的实现形态**:该是一张表,写成了一串 if。
