## A. CSRF 纵深(T2-MED / T15-M5,同族)

### A-1 先说反方:现有的 `SameSite=Lax` 已经挡住了经典 CSRF

跨站发起的 `fetch` / 表单 POST **不会**携带 `nx_sid`,这是浏览器行为,不需要我们做任何事。
所以本项**不是**「有个洞在流血」,而是纵深不足。若证伪方认为纵深不值这个复杂度,这是成立的论点,请直说。

### A-2 Lax 挡不住的三处残余

1. **同站不同源**:Lax 的「同站」按可注册域算。将来若有任何子域(`docs.` / `status.` / 第三方托管页)
   落在同一可注册域下且不完全可信,它发起的写请求会带上 cookie。
2. **带副作用的 GET**:Lax **会**在顶层 GET 导航时发送 cookie。`GET /api/publish/status` 有写操作,
   攻击者页面上一个 `<a>` 或重定向即可触发。影响有限(它做的事等同于下一次正常轮询会做的),
   但这是「Lax 恰好不保护的那一类」,不该留着。
3. **不实现 SameSite 的老浏览器**:占比在缩,但运营后台的受众可控性不代表攻击者的浏览器可控。

### A-3 提案

1. **自定义头**:所有**需鉴权的写接口**要求 `X-NX-Console: 1`。跨源请求要带自定义头必须先过 CORS 预检,
   而 worker 不回放行的 CORS 头 → 预检失败 → 请求发不出去。无需令牌存储、无需 double-submit。
   - 落点:一个中间件,挂在鉴权中间件之后、各写路由之前。
   - **豁免**(必须显式列举,不许「默认放行」):`POST /api/e`(公开埋点,无特权动作)、
     geo 直通兑换(公开设计)。豁免名单进代码常量,由审计覆盖测试断言其大小不增长。
2. **Origin 兜底**:`Origin` 存在且 host ≠ 请求 host → 拒。存在才判(同源 fetch 未必带 Origin),
   所以它只是兜底,不能替代第 1 条。
3. **把副作用移出 GET**:`GET /api/publish/status` 改为**只读**——超时版本在响应里算出「已超时」用于展示,
   实际落库改在 ①6h 巡检 cron ②下一次 `POST /api/publish` 发起时。

### A-4 波及面(动手前必须一起改,否则当场全红)

`worker/runner.mjs`(执行器带 cookie 打 API)· `worker/test-static.mjs` · `worker/test/*.spec.ts` 全部写请求 ·
`admin/src/api.ts` · `worker/README.md` 里的 curl 示例。**这一条是本提案最大的成本项**,请证伪方评估
「值不值」以及「有没有更小的做法」。

## B. 限速的 IPv6 纵深(T2-MED)

**现状**:限速键 = IP 原样。IPv4 下一个攻击者通常只有一个地址,per-IP 成立;
**IPv6 下最小分配单位通常是 /64**,同一攻击者手里就有 2⁶⁴ 个地址,per-IP 限速等于没限。

**提案**:键归一——IPv6 取 /64 前缀,IPv4 保持 /32(即原样)。

**代价**:同 /64 下的多个正常用户会共享配额。/64 通常对应单个家庭/站点,误伤面小;
IPv4 侧 CGNAT 本来就共享,不变差。

**⚠️ 待证伪方核**:Cloudflare 的 `CF-Connecting-IP` 在 IPv6 下给的是完整地址还是已归一的前缀?
若平台已归一,本项即为空操作,应当直接砍掉而不是实现。**这一条我没有实测,是本提案里最弱的断言。**

## C. 审计覆盖测试(T23-AC)

**做法**:`AUDIT_ACTIONS` 已经是封闭枚举(单一真源)。测试**从它枚举**,逐动作触发一次真实请求,
断言审计表落了对应行;枚举里有而测不到的 → 红,并点名是哪一条。

**红测**:往枚举里加一条没人写的动作 → 必须变红(证明它验的是「该有的在不在」,
不是「存在的对不对」)。

## D. CON16-AC4 配置结构版本漂移拒绝(T22 前置,挂账至此)

**做法**:载入/物化配置时,`schemaVersion` ≠ 当前 `SCHEMA_VERSION` → **拒绝并说明**,不静默物化。
拒绝面要出现在:发起发布的前置校验、执行器物化步、种子回放。

**⚠️ 待证伪方核**:回滚到旧版本时,旧 payload 的 schemaVersion 必然是旧值 —— 那么
「回滚走完整门链」(CON13)与「版本漂移即拒」会不会正面冲突,把回滚路径整条锁死?
若会,拒绝规则需要区分「草稿/新发布」与「回滚既有版本」,或者回滚时先升级 payload。
**这是本提案里我认为最可能撞车的一处。**
