# 官网自动发布

运营在后台保存草稿、检查改动并点击发布后，服务端自动调度执行器。界面显示发布步骤、失败原因和版本记录；刷新或关闭后台不会取消任务。日常操作不需要 PowerShell、cookie 或手动启动 CI。

本机由启动器托管独立执行器，使用单独服务凭证。生产使用 `.github/workflows/publish-website.yml`，只接收整数 `versionId`，从受保护的 `main` 触发并检出当次不可变 commit。站点固定为 `nexgrid-site-worker`，生产任务串行执行；D1 持久保存任务和调度记录，服务端回读本次上线印记后才确认 live。

每单锁定确认的草稿修订和配置快照，检查源码复制前后的完整摘要，在隔离目录依次执行：

1. 校验源码种子基线，物化本单的全部语言和站点配置，并逐字节核对。
2. 构建一份正式官网产物，所有正式产物门检查这一份内容；生产使用 `verify:prod`。检查前后摘要必须一致。
3. 构建后台并组装发布包，复核官网未变、后台复制一致及最终包摘要。
4. 切换本机快照或部署公网，再由服务端核实实际内容。回报中断只重试收口，不重复部署。

官网正式构建从两次减为一次；两种交互测试配置和发布器冷启动回归仍各自构建，成功路径合计四次 Astro 构建加一次后台构建。检查种类保留，相同输入的后台类型检查和门自检不重复运行。纯文案改动且源码指纹与上次全量一致时走增量：跳过源码静态门（worker 类型、自检红测、AI runtime 回归、worker 单测、发布器回归），跳过的门记名留痕、不冒充通过。每次发布的浏览器版面门始终全站实测；线上快照不能作为通过当前源码和检查门的证明。

发布检查遇到首个阻断项立即结束，未执行的检查不会记为通过；构建与私有测试资产就绪后，先运行后台配置、文案及其自检、埋点和 Worker 测试，再运行发布器故障回归，最后执行浏览器版面检查，避免快速检查的错误拖到最后才暴露。手动 `npm run verify` 仍汇总全部检查。每个命令最长执行 30 分钟，心跳和输出不能延长时限；超时先终止所属进程树并确认输出通道关闭，再收口失败。无法确认退出时保留现场并暂停接单。后台显示当前检查，断网时标明结果待核实。本机 API 退出后由启动器按 3～30 秒间隔自动重启，端口被占用时不会启动替身。

本机证据位于系统临时目录 `nexgrid-publisher-<仓库摘要>/evidence/`，按版本记录草稿修订、配置摘要、完整源码摘要、执行环境和正式/最终产物摘要，以及当前命令、开始时间、最长时限和脱敏输出。命令起止和检查进度立即保存，其余输出在 5 秒内保存，即使随后没有新输出也会落盘；每阶段最多保留末 32000 字符，服务端错误详情最多末 6000 字符。版面检查分别报告文字、弹层、导航、字体、菜单与卡片的当前路由序号，序号只表示检查位置，不表示通过。证据不包含配置正文和密钥；任务目录清理不删除这些记录。已核实成功后的清理错误作为维护问题保留。

后台每 2 秒读取进行中的状态，显示已完成步骤数、当前检查、最后更新时间和最近输出。执行器每 5 秒推送脱敏输出，明确进度变化立即推送；所有推送先保存证据，按顺序送达，步骤结束前等候推送完成，防止迟到的进度覆盖终态。旧版纯文本记录仍可查看。

已开工任务超过 1 分钟没有本单心跳时，后台显示“发布状态待核实”，保留最后输出并提供刷新入口。判断使用服务端的当前任务心跳，安静的长检查不会因缺少输出被误报；新空闲执行器的心跳也不能掩盖旧任务失联。状态接口断连时单独提示连接问题，均不擅自判定失败、取消或重发。

刷新失败保留已收到的任务和日志，状态轮询恢复后继续更新；发布前检查信息未刷新成功时单独保留重试提示，避免把旧检查结果当作新结果。

检查失败后停止后续步骤，直接显示原因、处理建议和完整错误详情入口。缺译使用“一键补译缺项”，优先补齐已有默认译文，再由 AI 处理剩余项，保护人工修改；异步补译写入草稿后自动刷新发布检查。代码或依赖错误由维护人员修复，不提供从浏览器执行任意命令或改写源码的接口。“重新检查并发布”会重新核对最新草稿，再进入原有发布确认，不会沿用过期修订或跳过检查。

## 一次性生产配置

由维护人员完成账号、资源和密钥接入；运营日常无需介入。

1. 在 `agentabatiuo572-byte/nexion-website` 创建 GitHub `production` environment，仅允许受保护的 `main` 发布。该环境不要设置每次运行必须人工批准，否则后台点击后会停在等待审批。保护 workflow、执行器、门脚本和依赖锁文件的修改权限。
2. 创建真实 Cloudflare D1、KV，并对 D1 应用仓内迁移。将现有 Worker、域名和初始已验证站点部署到固定的 `nexgrid-site-worker`；初次接入由维护人员完成，不能用尚未上线的后台自行引导首次部署。
3. 在 GitHub `production` environment 设置下表变量与 Secrets；在 Worker 中设置发布模式和两枚服务 Secrets。生成器拒绝空值、占位资源和非公网 HTTPS API 地址，开发用变量不会被带入生产文件。

| 位置 | 名称 | 内容 |
|---|---|---|
| GitHub environment variable | `CLOUDFLARE_ACCOUNT_ID` | 目标 Cloudflare 账号的真实 ID |
| GitHub environment variable | `PUBLISH_D1_DATABASE_ID` | `DB` 绑定对应的真实 D1 ID；名称沿用 `nexgrid_site` |
| GitHub environment variable | `PUBLISH_KV_NAMESPACE_ID` | `KV` 绑定对应的真实 namespace ID |
| GitHub environment variable | `PUBLISH_API_URL` | 固定 Worker 的公网 HTTPS origin，不含路径、参数或凭证 |
| GitHub environment secret | `PUBLISH_RUNNER_TOKEN` | 独立随机服务密钥，与 Worker 中同名 Secret 一致 |
| GitHub environment secret | `CLOUDFLARE_API_TOKEN` | 仅授目标账号发布所需权限的部署令牌；不使用全局 API key |
| Worker secret | `PUBLISH_GITHUB_TOKEN` | 仅目标仓库的 Actions 写权限，用于自动触发 workflow；不交给 runner |
| Worker secret | `PUBLISH_RUNNER_TOKEN` | 仅允许执行器领取、心跳、状态和步骤回报，不是管理员登录凭证 |
| Worker secrets | `SETUP_TOKEN`、`BEACON_SALT`、`BYPASS_SECRET` | 生产独立密钥，禁止沿用开发值 |

生成配置固定写入 `ENVIRONMENT=production`、`PUBLISH_EXECUTION_MODE=github`、`PUBLISH_GITHUB_REPOSITORY=agentabatiuo572-byte/nexion-website`、`PUBLISH_GITHUB_WORKFLOW=publish-website.yml`、`PUBLISH_GITHUB_REF=main`。Wrangler 生产配置位于 CI 临时目录，保留仓内绑定与 cron，资产目录必须是本次已验收的 `dist-live`。隔离执行器使用同一个生成器重新定位源码、资产和迁移路径。密钥只经 Secrets/进程环境传递，不写入配置、公开资产、workflow 输入或日志。

## 故障与验收

机器接口遇到连接中断或服务端 5xx 时，每次调用在同一个最长 8 秒请求期限内重试原请求。进度上报暂时不可达时，本地检查和证据保存继续，执行器在现有心跳租约允许的时间内重试上报，恢复后继续当前任务；不会重新构建或重复切换。进度及阶段确认每次最多等待 30 秒，积压输出只补报最新一份；阶段切换仍须重新确认任务归属和服务端步骤状态。身份或任务归属拒绝、证据无法持久保存、心跳连续失效达到 30 秒宽限时停止；真实检查失败仍立即停止后续步骤，不等待进度补报，并保留原始错误。

停止命令通过现有进程间通信交给监护进程，监护进程终止实际命令树并保留清理责任。Windows 终止工具每次最多运行 5 秒，失败后间隔 500ms 重试；命令根进程已消失但终止未获确认时不再追杀可能复用的 PID。只有收到停止确认且输出通道确实关闭，才持久解除退出待核实标记；迟到确认也可完成收尾，再由现有启动器恢复原任务的失败记录。确认或持久化失败时保留现场，不自动重跑、不继续发布，也不将“停止处理中”说成已经停止。

本机 Wrangler 4.127.1 曾将代理请求的 `Network connection lost` 升级为整个开发服务退出；同型错误已有[上游回归报告](https://github.com/cloudflare/workers-sdk/issues/15317)。启动器自动重启与执行器断线恢复处理这一故障，但不表示上游连接问题已经修复。

标准 `publish:runner` 命令为发布器主进程增加 `--no-maglev`，作为 Windows 上 Node 原生异常退出的兼容处理；参数不传播到检查子进程。AI 运行时回归在 `pretest` 和发布门中均单独使用该参数，其默认启动曾出现原生异常退出。证据记录 Node 版本及实际启动参数是否包含此选项。该处理参考[相似上游报告](https://github.com/nodejs/node/issues/62260)，本机没有留下原生调用栈，不能据此认定崩溃根因。进程意外退出后，原任务仍停止并保留失败记录，不自动重跑或跳过检查。

升级已有安装时，先应用全部 D1 迁移（包含 `0016_publish_source_draft_rev.sql`），再部署新版 Worker。本机执行器的空闲心跳、生产每分钟的维护任务在没有活动发布时准备新版草稿；日常读配置和发布检查不迁移已有草稿。准备未完成前服务不宣告就绪。

每次改变转换逻辑使用独立升级编号，已执行的编号不能代替实际结构校验。原草稿与修订号同事务备份，已有标题等修改保留；历史版本不重写。旧默认值安全转换，无法识别的定制内容明确报冲突并保留原稿。重复准备不会覆盖升级后的编辑；回滚旧版只转换待发布副本，仍须通过全部检查。

生产调度未配置时应在发布前明确拒绝。调度或 CI 初始化失败不能伪造步骤成功；后台通过调度重试、任务租约和超时记录给出失败原因。门红时保留草稿与上一版；若部署已发生但确认中断，必须核对实际印记再收口，不能直接声称线上未变。回滚仍从后台选择历史版本并走完整发布链。

Windows 本机目录被占用时，快照切换会降级为逐文件同步，可能短暂新旧混排。本机发布不能作为公网原子部署的验证依据。

正式开放前，维护人员须实际验证：后台点击一次自动上线、刷新后版本一致；重复触发只执行一次；门红不换线上；执行器重启和回报丢失有明确结果；本次部署内容与版本印记一致。当前仓库的 Cloudflare 资源仍是占位，代码与本地测试不代表已经部署或通过真实生产验收。

接口依据：[GitHub workflow dispatch](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)、[Cloudflare 版本与部署](https://developers.cloudflare.com/workers/versions-and-deployments/)。
